# Windows 原生快速截图原型 v0.1

日期：2026-10-29。范围：验证原生框选路径，尚未迁移完整标注或录屏界面。

调研背景：[截图与录屏架构调研](capture-architecture-research-2026-10-29.md)。

## 如何体验

进入「工具 → 截图」，将「截图模式」切换为「原生快速（试用）」。本次运行中的截图按钮和已配置的截图快捷键都会使用该原型；重启后恢复默认的「完整标注」。模式切换不是全局快捷键重新注册，不改变用户原来的按键配置。

拖动框选，松开后按 Enter、Ctrl+C、双击选区，或点击对钩复制；Esc、右键或 × 取消。支持反向拖动、选区边界裁剪和按显示器物理像素复制。小于 2 × 2 像素的选区不会复制。

切回「完整标注」可继续使用画笔、箭头、文字、马赛克、保存、贴图及 OCR。录屏沿用现有实现。macOS/Linux 不显示原生试用入口。

## 实现路径

```text
截图按钮 / 原有快捷键
  → 保存助手的可见、最小化、焦点状态
  → 必要时隐藏助手
  → Rust/GDI 取一次桌面 BGRA 位图
  → Win32 窗口 + Direct2D 显示位图、选区和确认按钮
  → 复制时才裁剪、编码 PNG 并写系统剪贴板
  → 销毁原型窗口，释放图像/绘制资源，恢复助手原状态
```

原型唤起期间不编码 PNG、不创建截图草稿、不通过 IPC 传输底图、不创建捕获 WebView。现有完整模式仍可使用并预热自己的 WebView，因此当前整个助手的内存不代表“完全移除旧捕获层”的最终占用。

`desktop_snapshot.rs` 提供共享的内存 BGRA 捕获；完整模式继续在导出路径转换 RGBA、编码 PNG。`native_capture.rs` 负责独立 Win32 消息循环、Direct2D 位图绘制和 DirectWrite 文本，不向 Tauri 再添加另一个跨平台 GUI 事件循环。

原型在工作线程上使用每显示器 DPI 感知，退出后恢复线程原来的 DPI 上下文；COM、窗口、图像与剪贴板缓冲有对应释放路径。空闲时没有原型窗口，也不持续取屏。首次使用后的字体、驱动等系统缓存仍可能保留，不能据此承诺进程内存立即回到启动数值。

窗口无默认背景刷，先准备位图和绘制资源，再显示并在首个原生 WM_PAINT 提交完整画面，避免空白底色帧；隐藏期间不提前向 HWND 提交绘制，减少被遮挡窗口的提交等待。首帧提交后发出本地 `native-capture-ready` 事件，记录取屏、资源准备与原生就绪耗时，供开发对照使用。正常返回包括 `copied` / `cancelled`；重入请求会被拒绝。

## 剪贴板

同时写入标准 CF_DIB 和注册的 PNG 格式。CF_DIB 是顶向下的 32 位 BGRA，裁剪后强制不透明；PNG 在复制时转换为 RGBA。裁剪、编码和分配缓冲在打开全局剪贴板前完成，减少占锁时间。写入成功的缓冲所有权交给 Windows；未转交的缓冲由原型释放。

复制失败时保留选区并显示错误，允许重试或取消。取消不会改写剪贴板。

## 已完成验证

- TypeScript/Vite 构建、Rust 检查、47 项前端测试通过；新增测试覆盖快捷键原生分流、无 PNG 草稿 IPC、重复触发拦截、取消/失败后的窗口状态及完整模式保留。
- Rust 测试覆盖反向拖动、显示器边界裁剪、无效选区拒绝、像素通道、行序及透明度。
- Windows 4K 桌面实测：原型窗口可见、冻结底图和原生选区/按钮正常；Esc 取消、重复调用拒绝、助手最小化状态保留。
- 实际复制反向拖出的 200 × 150 选区：PNG 与 CF_DIB 的尺寸、逐像素内容、通道和顶向下行序一致，并与取屏参考区域相符。整个原型流程没有新增截图草稿。

性能记录以开发版和当前测试设备为边界；原生 `readyMs` 从 Rust 捕获入口开始，到首次可见绘制完成并等待合成器提交为止，不包含前端按键处理。跨模式比较应使用统一的外部计时口径。

## 本机对照记录

环境：Windows、3840 × 2160 显示器、150% 缩放，Tauri 开发构建；助手开始捕获前处于最小化状态。同一进程中交替使用真实 Ctrl+Alt+A 截图快捷键，计时从发送快捷键开始，到捕获界面就绪并取得键盘焦点为止；用真实 Esc 取消。每种模式三次，属于小样本开发观测，不代表发行版、其他设备或微信的性能。

| 轮次 | 完整模式就绪 | 原生原型就绪 | 原生取屏累计 | 原生资源准备累计 | 原生首帧提交累计 |
| --- | --- | --- | --- | --- | --- |
| 1 | 850 ms | 712 ms | 144 ms | 235 ms | 618 ms |
| 2 | 808 ms | 608 ms | 140 ms | 240 ms | 515 ms |
| 3 | 842 ms | 589 ms | 138 ms | 243 ms | 473 ms |
| 中位数 | 842 ms | 608 ms | — | — | — |

前三列采用外部统一计时；后三列是从 Rust 入口起算的累计时间，不能相加，也不能直接当成完整快捷键响应时间。当前这组热调用中位数减少约 28%，但数据不足以给出稳定的 P95 或“无闪屏”保证。

进程重启后的另一组直接调用，首个原型请求观测到 1243 ms 的外部就绪时间，随后两次为 335 / 380 ms。首个请求中资源准备累计为 1158 ms，取屏累计为 197 ms，说明首次图形/文字资源初始化成本明显。直接调用与真实键盘对照不是同一计时起点，分别记录，不挑选其中最快值作为产品响应结论。

捕获后的进程内存存在图形驱动、字体、分配器和浏览器缓存波动；旧完整模式的预热 WebView 还保留着，目前没有证据证明整个助手的常驻内存已降低。需要在迁移方案确定后，再用发行构建、长时间空闲和连续操作进行资源对照。

## 尚未迁移

原型不包含标注工具、文字编辑、撤销/重做、另存、贴图、OCR，也不是 macOS/Linux 的新实现。系统级窗口识别、混合 DPI 多屏、HDR、远程桌面及设备切换仍需后续验证。单次首帧耗时或截图不能证明所有设备都没有闪屏。

下一阶段应以同机响应分布、连续使用后的资源变化和实际屏幕观感决定是否迁移完整编辑器；不按“Rust/原生”名称预设性能结论。

本轮结果支持继续验证原生路线，但尚不足以直接切换生产默认。后续优先测量并优化图形/文字设备初始化、首帧提交，以及快捷键经过主 WebView 的调度开销，再决定哪些轻量资源应复用、哪些图像资源应在空闲时释放。
